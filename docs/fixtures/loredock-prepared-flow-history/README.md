# Ordered history controls

The [history case helpers](../../../scripts/loredock-prepared-flow/history-cases.mjs)
separate actual capacity creation from later browser, restart, source revocation and
accounting observations. The [ordinary rehearsal](../../../scripts/loredock-prepared-flow/ordered-history-development.mjs)
runs that subset in its final relative order. It uses only the reusable permit sources,
actual protected HTTP routes, production entry and declared controlled runtime.
No application code, model, reserved-family observation or resource acceptance is added.

## Creation and stopped checkpoints

Creation starts a fresh catalog, indexes/analyzes its original sources, then completes
64 actual reviewed prepared admissions with nonempty native witnesses. It records every
creation and the list responses at 1, 20 and 64 retained attempts. At 20 and 64, one
additional real Ready supplies the declared transient-restart control. Stopping the
controlled daemon permits complete copied checkpoints. Creation resumes after the
20-row copy and finishes before any browser, history-reopen, revocation or accounting
case. It makes exactly 64 controlled calls across its two process segments.

At capacity, the 65th admission returns `ANSWER_WITNESS_LIMIT` before another runtime
call and leaves the current Ready usable. Replaying the first request returns its exact
original response bytes. Witness payloads total 1,326,720 bytes at 20 rows and 4,245,504
bytes at 64. No capacity rows are seeded with SQL.

Every subsequent case verifies the complete checkpoint inventory before copying it
into a fresh owned directory, and verifies the original checkpoint again after stopping.
Production-entry observations and diagnostic accounting use separate copies. HTTP
response metadata now includes the hash of its retained raw body; comparisons require
the same bytes, not just equivalent selected JSON fields.

## Ordered observations

| Stage | Ordinary outcome |
| --- | --- |
| Browser at 20, then 64 rows | Actual page, Ready and saved answer remain open for 30 seconds each; desktop and 390px screenshots, HTTP traffic and passive metrics retained. About five API requests per second in each interval. |
| Production restart at 20, then 64 | All 20 plus 64 saved answer bodies and both list bodies match their original hashes. The previous transient preparation IDs disappear. Replaying the first admission returns the identical saved body. |
| Revocation at 64 | Revoking the independent notes source fences all 64 answer reads and removes context, native context and answer text. All 64 witness rows remain as purged tombstones, with zero witness payload bytes. |
| Accounting at 20, then 64 | Both requests return the exact resource-lane list bytes. Each reads twenty visible witnesses through twenty actual budgets totaling **3,168,560 units**. No preflight/provider calls, unclosed budgets, unscoped budgets or late accounting activity. |

The two list totals exceed the unchanged **1,000,000-unit aggregate ceiling**. Browser
sampled maxima are **1,347,727,360** and **1,380,564,992 bytes**, both above **1 GiB**.
The 20-row browser records one explicitly incomplete startup sample: a process exits
during the first census. The 64-row census records no such race. Incomplete observations
are retained and never silently converted into a zero or a passing resource result.
The sequential sampler still has the lifetime-attribution limitations documented in the
[preceding checkpoint](../loredock-prepared-flow-matrix/README.md).

## First failure and correction

The first rehearsal completes all 64 admissions, but fails before starting the first
browser. A `readOnly` SQLite connection can still create WAL/SHM sidecars. Reading
storage statistics from an already hashed checkpoint changes its directory, and the
pre-copy integrity assertion rejects it. Both original database files retain their
recorded hashes; the extra sidecars and full failed output remain available. A secondary
cleanup error attempts to inspect a destination that was never copied; that original
error is also retained.

The corrected helper inspects the stopped working directory before copying and hashing,
then never opens the retained checkpoint with SQLite. Later inspection uses a separate
copy. Cleanup skips destination storage inspection when copying never happened. The
[regression test](../../../scripts/tests/loredock-history-checkpoint.test.mjs) uses actual
SQLite WAL behavior to reproduce the sidecar creation and verify unchanged checkpoint
bytes. The second complete rehearsal passes its eight functional stages in 155.8 seconds.
The first run remains failed; no original output is replaced or retried into acceptance.

driver bytes, stopped catalog copies and logs. Both external owners report zero surviving
descendants and no owner errors; the first driver exits 1 and the second exits 0.

admission's saved-answer hash matches an actual retained GET response.

unchanged application/input seal validates with zero reserved-family candidate reads.
