# Reusable purge-recovery and original-evidence faults

The [case functions](../../../scripts/loredock-prepared-flow/catalog-fault-cases.mjs)
reuse verified stopped synthetic history/cold checkpoints. The
[ordinary entry](../../../scripts/loredock-prepared-flow/catalog-faults-development.mjs)
runs pending-purge recovery over 64 actual prior admissions, then missing/corrupt
required-original cases on separate empty catalog copies. The existing declared-fault
case owner is shared with validator cases. Every launch, including production inspect,
fault and recovery entries, keeps explicit fault provenance and excludes timing from
resource qualification. No application method is wrapped or real provider invoked.

## Pending cleanup of 64 stored answers

The input history comes from 64 real controlled HTTP admissions retained in the earlier
history control. This case does not regenerate or seed that history. It independently
checks that the selected notes source is an authorized dependency of every attempt and
is uncited in every saved context.

A declared SQLite trigger makes witness cleanup fail. Actual source revocation returns
the expected HTTP 500, yet all 64 subsequent answer responses are already fenced with
null original context, compact context and answer text. The stopped pending checkpoint
retains the revoked/pending source, injected trigger and 64 unpurged witnesses containing
4,245,504 bytes. Those synthetic bytes are intentionally retained as recovery evidence;
this checkpoint is separate from the recovered working catalog.

The case removes the trigger only from its working copy, then starts the actual
production entry. Startup completes the pending purge. All 64 original attempt IDs and
witness tombstones remain, but stored context/results are null and witness text totals
zero bytes. All 64 API responses stay fenced. Exact same-request replay returns the
existing first attempt without adding an admission. The original input and pending
checkpoint remain closed and unchanged.

## Required originals cannot be replaced

Each refusal case prepares useful native context and holds actual runtime preparation
before dispatch. It then deletes one required original span or changes its stored text
inside that case's isolated catalog. Both attempts fail with no answer, dispatch or
usage receipt. Runtime counters are one prepare, zero runs and one close. No provider
request/output file exists; replay returns the exact failed response. The original
prepared context and intact witness remain available for inspection.

The recorded reasons distinguish unavailable/revoked evidence from a stored-evidence
integrity failure. Missing or corrupt originals are not silently replaced by compact
derived text or a new preparation. These are explicit faults; they do not manufacture
an oracle expectation or count as a naturally observed incomplete positive.
