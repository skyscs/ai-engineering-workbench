# Task 119 — Specify native connected-path context for project questions

Status: scoped, 2026-11-04. Start after Task 118 exact-head acceptance.

Return to the LoreDock-first goal: help a project question use the connected source
context already available across repositories. This task is a source-backed design and
bounded evaluation contract, not a production answer change or a new model evaluation.

Audit the current Ask Project retrieval, preview, immutable input/history, citations,
correction semantics, authority and prompt budgets against native path projections and
recorded originals. Identify the smallest useful next consumer. Distinguish current
question-selected connections from explicitly chosen recorded history; do not quietly
use an arbitrary saved path or combine an old source vector with current answer evidence.

Define selection relevance, complete supporting-original admission, source/epoch pins,
omission/ambiguity statements and one complete operation budget before prototyping.
Existing literal retrieval must remain available; a static connection is a reading clue,
not proof of runtime behavior or a root cause. The new context must not bypass parser
gaps, fabricate repository roles, inherit unrelated engineer corrections, increase fixed
prompt/evidence caps or let source instructions become tool instructions.

Compare viable integration choices, document the chosen boundary and scope the smallest
offline feasibility task. Freeze a fresh ordinary owned fixture and prospective questions,
required original/relationship support, useful scope bounds, abstention cases and measurable
resource/counter checks before executing that comparison. Include overlapping topics,
irrelevant roots, missing consumers, incompatible/evicted inventories, stale source vectors,
source/policy changes and full-support overflow. Preserve raw failures and distinguish
mechanical support from semantic quality or independent acceptance.

Keep production code, answer formats/prompts, runtime configuration, existing history and
all exhausted evaluation families unchanged. Do not perform model calls, delete saved
records, touch corporate sources, mutate the user's demo or implement the Workbench bridge.
Do not add storage CRUD solely as a prerequisite to this context design. Record what would
need an ADR/schema change and what remains a separate future task. Publish and review the
design with existing documentation/link checks; only implement its explicitly scoped
follow-up after exact-head CI acceptance.
