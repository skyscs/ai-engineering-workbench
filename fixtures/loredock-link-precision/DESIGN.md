## Proposed structural-subject admission

Start with the same primary lexical seeds, original-passage anchors, one-hop limits,
ordering, source ownership and full original support as v1. Before selection:

1. Retain only HTTP-target, event-delivery, contract-match and contract-difference edges.
   Configuration equality/difference stays available in the declaration map, but cannot
   alone propose an additional component. This intentionally loses some contextual hints.
2. Require a distinctive question term in an explicit relationship subject. For HTTP use
   endpoint path properties; for events use the publisher payloadType; for contracts use
   the contract name and field names from both endpoints. Normalize with production
   searchText. Match whole tokens, not substrings. Preserve differences and uncertainty.
3. Ignore source labels, free-text reasons/gaps, generic field types, header names,
   versions, runtime topic expressions and unrelated properties as subject anchors.
   They can remain original evidence but do not establish subject affinity in this rule.
4. The existing endpoint-owned original passage anchor is still required. This proposal
   does not prove runtime identity or causal relevance, and does not add parsers or evidence.
