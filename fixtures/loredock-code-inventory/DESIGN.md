# Complete synthetic code-fact inventory — premeasurement contract

Task 041 indexed 3,679 files but its interactive code projection examined only 100 of
3,621 candidate files. Measure the cost and provenance of applying the existing bounded
parsers to every eligible indexed code file before designing persistent analysis.
This experiment changes no production parser, graph limit, database schema or model input.

## Fixed inputs and execution

Use one fresh, owned, full Task 041 volume fixture with its frozen manifest/revision vector.
Perform one initial production index at current defaults. If it does not publish, record
the outcome without resume/retry and leave parsing unavailable. No unchanged refresh or
replacement of Task 041 capacity results. No corporate sources, remote clone or model.

On the published index, record the ordinary code/declaration projections and their actual
limits/omissions. Then perform two fixed sequential file-by-file extraction passes over
the same pinned index, with current Java/TypeScript/Vue/AMD parser implementations. The
second pass repeats parsing; it is not a cache hit, refresh or independent corpus.
Freeze the parser/dependency hashes and this protocol before measurement.

Enumerate candidate file metadata from the authorized published catalog, using the same
extension predicate/dispatch as the current projection. Preserve its 32 KiB/file and
eight-span/file guards and each parser's syntax/symbol limits. Add explicit experiment
bounds of 10,000 candidate files, 50 MiB examined text, 128 KiB serialized facts per file,
16 MiB retained raw facts and five minutes per pass. Visit saved source order then path;
check total budgets between files and stop with explicit unattempted records. A per-file
fact limit rejects that file's derived output without substituting a truncated claim. Never
raise production limits. Record every excluded, failed or unattempted file and reason;
parse success does not establish complete language/framework understanding.

Read each admitted complete document through the production evidence validator. Verify
its source/revision/blob/content and every issued span against owned Git. Cache only the
previously verified Git text for the identical owned source/revision/path when checking
the repeat pass. No generated code, configuration, plugins or imports are executed.
For each symbol/operation, validate UTF-16 string offsets inside the source, calculate original line
ranges and retain source support. Calls and record signatures retain whole-file support.

Record raw parser facts and gaps, version/input/fact hashes, serialized fact bytes, per-source
and per-language counts, file/read/provenance/parser durations and sampled evaluator RSS.
Yield between files so sampling/progress remain observable. Child Git memory and OS cache
isolation are outside the measurement. Separate these phases; do not treat validation/Git
overhead as parser-only cost or promise a production latency target.

## Checks and decision

Compare per-file fact hashes across the two declared passes. Check the three frozen exact
symbols in the final added files. Verify every default code-projection symbol has matching
original ranges in the full inventory. Separately list same-source exact handler names
whose method syntax becomes available outside the bounded projection. This is source
availability, not proof of route binding, runtime execution, security or root cause.

Keep all unsupported syntax and unknown runtime behavior visible. Examining every file in
this simple generated workload does not establish realistic framework cost or semantic
acceptance. Ordinary CI uses a small owned shape and meaningful budget/provenance checks;
the full probe remains explicit. No rerun or parser tuning follows observed output.

Use the results to scope the smallest persistent-analysis or query-time follow-up. A new
cache/worker/storage contract must separately address authorization/purge, parser version,
immutable source evidence, interruption, reuse validation and retention. Do not implement
that architecture as part of this feasibility measurement.
